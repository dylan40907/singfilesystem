# Roles and page permissions

## The rule, up front

**Adding a page? Two places, same change:**

1. `lib/pagePermissions.ts` — so the role editor can grant or deny it.
2. `public.page_data_tables` — so the database lets a grant actually read and
   write the page's data.

Miss the first and the page is invisible to the role editor: nobody can be given
access to it and nobody can be kept out of it, so it silently falls back to
whatever role checks happen to be hardcoded around it. That's exactly the mess
this system replaced.

Miss the second and the grant is cosmetic. The tab appears, the page opens, and
every query comes back empty or every save fails with a permission error. That
is what happened when Timesheets was granted without a policy on `hr_employees`:
the hours loaded and the names didn't.

## How it works

A role is **a base level plus per-page overrides**.

- **Base level** — `teacher`, `supervisor`, or `campus_admin`. Stored in
  `user_profiles.role`. This is what the older row-level security policies
  understand, and it did not change when custom roles were introduced, so every
  existing policy still works.
- **Overrides** — rows in `hr_role_permissions` saying a specific page is
  `none` / `view` / `edit` for that role.
- `user_profiles.hr_role_id` points at the custom role, or is null for "just the
  level's defaults".

Full admins (`role = 'admin'`) bypass all of it and always get `edit`.

### Why not just add more roles to the enum?

That's what was happening. "App Supervisor" was a supervisor plus a
`can_manage_learning` boolean column, and each new variation would have meant
another column and another special case in every nav component. Now it's data.

## Adding a page

1. Add an entry to `PAGES` in `lib/pagePermissions.ts`:
   - `key` — stable, stored in the database. **Never rename one in place**; a
     rename orphans every override pointing at the old key.
   - `editable` — `false` for genuinely read-only pages, so the editor offers
     On/Off instead of a meaningless View/Edit choice.
   - `defaults` — what each of the three levels gets when a role says nothing.
2. Add the tables the page reads and writes:

   ```sql
   insert into public.page_data_tables (page_key, table_name, write_allowed) values
     ('hr.newpage', 'hr_new_thing', true),
     ('hr.newpage', 'hr_employees',  false);   -- reads names, must not edit them

   select public.rebuild_page_grant_policies();
   ```

   `write_allowed = false` means even an **edit** grant on that page only reads
   that table. Use it for anything the page displays but doesn't own — employee
   records, campuses, lookup lists. Editing a timesheet must never imply editing
   the employee it belongs to.
3. Put the route under a section layout so `PageAccessGuard` covers it
   (`app/admin/hr`, `app/admin/sales`, `app/admin/students`, `app/admin/courses`,
   `app/admin/learning`). The guard resolves the page from the pathname, blocks
   what the role can't view, and shows the read-only banner for a `view` grant.
4. Inside the page, call `usePageAccess()` and hide edit controls when
   `readOnly`.

### Checking your work

Every table a page queries should appear in the map. To find gaps, grep the
page's sources for `.from("…")` and compare against:

```sql
select table_name, write_allowed from public.page_data_tables
where page_key = 'hr.newpage' order by table_name;
```

## The security boundary

`resolveAccess` decides **navigation and whether edit controls are offered**.
It is not the security boundary — RLS is.

Every table in `page_data_tables` carries two generated policies:

```
page grant view <table>   FOR SELECT  USING  (has_page_access('<page>','view') OR …)
page grant edit <table>   FOR ALL     USING/WITH CHECK (has_page_access('<page>','edit') OR …)
```

They're generated by `public.rebuild_page_grant_policies()` rather than written
by hand, so ~150 policies can't drift out of step with each other. The function
drops everything named `page grant %` and rebuilds from the map, so it is safe
to re-run and is the only thing that should ever create a policy with that name.

Helpers available in SQL:

- `public.my_page_access(page_key)` → `'none' | 'view' | 'edit'`, or null when
  no override applies.
- `public.has_page_access(page_key, min)` → boolean.
- API routes can't use either (no browser session): use
  `serverHasPageAccess()` from `lib/serverAccess.ts` with a service-role client.

Both know about **overrides only**, not base-level defaults. Defaults live in
TypeScript, and duplicating them into SQL would give two copies to keep in step.
Base-level behaviour is already governed by the existing policies that key on
`user_profiles.role`.

## Things that are deliberately not grantable

- **`hr.roles`** — whoever edits roles can grant themselves anything, so it is
  admin-only and `resolveAccess` hard-codes `none` for it regardless of any
  override.
- **Deleting the three built-in roles** — `is_system` roles can be edited but
  not deleted, since deleting the role every teacher holds would orphan them.
- **`curriculum.*`** (Files, Chat, Albums) has no page-grant policies. Those
  three already have their own rules — folder permissions, conversation
  membership — and every base level gets them by default, so there is nothing
  for a grant to open.

## Gotchas

- **A grant widens; a deny only hides.** Setting a page to `none` removes it
  from the nav and blocks the route, but it does not revoke access the base
  level already has in RLS. Denying Employees to a campus admin hides the page;
  it does not stop the API from returning employees to them. Use the base level
  for boundaries that must hold, and overrides for what people should *see*.
- **Page grants are not campus-scoped.** A teacher granted Timesheets sees every
  campus's hours, not just their own. Campus scoping still comes from the base
  level (`campus_admin` + `user_profiles.campus_id`).
- Deleting a custom role puts everyone holding it back on their base level's
  defaults. The UI warns with a headcount first.
- A role's `base_role` must match the level; the `admin-change-user-role` edge
  function re-checks this rather than trusting the client.
- Overrides are only stored when they **differ** from the base default, so a
  role automatically follows future changes to its level's defaults instead of
  freezing a copy of today's answer. It also means an override you set to the
  same value as the default won't be saved — that's expected, not a bug.
- The roles page shows who holds each role on its card. Two similarly-named
  roles are easy to mix up, and editing the empty one looks exactly like the
  permission system ignoring your change.
